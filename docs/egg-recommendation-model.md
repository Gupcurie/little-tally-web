# 放蛋实时推荐模型

每轮的配额为 `r_i`，总数为 `T = Σ r_i`。按实际记录求数量 `c_i`，完成轮数
`q = min floor(c_i/r_i)`，本轮进度 `p_i = min(r_i, c_i-q*r_i)`。
只有 `p_i < r_i` 的物品可以被推荐。超前数量保留，不能挤占当前轮的缺项。

使用带配额约束的分层随机调度。每个物品的理想间隔 `P_i = T/r_i`，下一次的
虚拟出场时刻为 `D_i = (p_i+0.5) P_i + U(-a_i, a_i)`，其中
`a_i = min(2, 0.3 P_i)`。优先考虑虚拟时刻较早者。在相差两次拿取以内的候选里，
尽量保持比例相关的间隔，并避免连出和 A B A B。若仍能不连出地完成剩余配额，
先保留这种可能，防止前面耗掉其他物品，最后被迫连放。

随机数来自 Web Crypto `getRandomValues`，不使用固定轮次种子或重复的出场表。
当前建议在页面重绘时保持稳定，只有实际记录、比例变化或用户主动换一个时才改变。
实际拿了其他物品，也会重新计算。跨轮保留实际放置历史，稀有项的间隔不会清零。
手动设数不是实际出场，不把批量设数伪造成连续放置历史。

数量精确是硬约束。间隔、避免重复和随机性是尽量满足的目标；高占比、手动拿取、
大量超前或某些配额已经耗尽时，无法同时严格满足所有目标。

安全边界：这是工作人员使用的客户端推荐器，不是防作弊的服务器抽奖系统。
即使随机数不可预测，公开的每轮配额及已出数量仍会泄露轮尾剩余奖品；客户端逻辑
也能被查看和修改。若需要防玩家读取或操纵，应另行设计由服务器持有秘密状态、
校验权限并记录抽取结果的方案。严格配额本身造成的轮尾推断仍然存在。
