# Shared comparison labels and temporary placement catalogs

Daily placement cards retain their member-specific labels. Matching uses a separate shared label per item ID so an explicit placement rename (娃衣 → 娃衣q) is visible to dismantlers. The previous implementation intentionally restored canonical names on save and then served those canonical names to dismantlers; refreshing could never show the placement member's new private label. This was reproduced against the production PostgreSQL functions in a rollback transaction before changing them.

Migration 20261113221716_shared_comparison_names.sql introduces private, RLS-protected comparison_names. Only an explicit change from the member's previous displayed name updates it. Regular counts, recommendation saves, joining with personal aliases, and replaying an old mutation cannot revert it. Both jobs' daily comparison RPCs use the shared label. Item IDs, quantities, ratios, mapping connections and role restrictions remain independent of this label. Existing historical aliases are recovered only when there is one distinct non-synonym candidate; conflicting old aliases are not arbitrarily ordered. No future recommendation data is added to comparison responses.

The frontend refresh button now renders a disabled busy state, loading text, a persistent completion timestamp and success/failure toast. Requests already in flight are awaited rather than silently skipped. Automatic rendering does not recursively retry a failed read or refetch endlessly when the comparison revision is ahead of the local projected ledger revision. Explicit refresh and the existing five-second interval can retry.

Migration 20261113222444_daily_catalog_scope.sql records provenance for categories automatically imported when a member joins placement in an existing daily room. Multiple members may hold the same imported category. When the last such placement member switches away, unused imported categories are removed from the shared book. Any real record, explicit rename, ratio/photo edit promotes the category to a formal shared category. Manually added categories are formal from the start, including zero-count ones. Historical records are preserved even when their net count has returned to zero. Pruning invalidates the placement edit revision and recommendation, so stale clients cannot reintroduce removed items through an old save. It does not change sales or any count records.

An initial repair was scoped to test account 123's current daily-room orphan categories: the account had switched back to dismantle, there were no records for those categories, and no other active placement member referenced them. It removed 20 unused egg definitions. A private comparison with the pre-deployment database backup verified that all 52 book record arrays across the 13 existing team ledgers were unchanged. Categories with records were retained, as the user clarified.

Both provenance and comparison-label tables are private with RLS and no direct authenticated/anonymous grants. The existing authenticated public wrappers, per-role compare-and-swap checks, and mutation replay journal remain authoritative. Legacy implementations moved to revoked private helper functions; none is a public bypass. Imports are tracked only for existing daily rooms; ordinary teams and personal ledgers keep their behavior. All mutations use the existing team advisory lock.

Tests: 45 related Node tests; Chrome mobile matching test with dismantle projection, delayed refresh, error and recovery, renamed remote placement item, preserved mapping and counts; production PostgreSQL BEGIN/ROLLBACK tests using synthetic accounts. Run matching-database.sql, shared-comparison-names.sql and daily-catalog-scope.sql inside one rollback transaction after the required schema exists. The matching test temporarily detaches daily-room lookup rows, so never run the SQL test body without the rollback wrapper. Live smoke uses a temporary personal QA account and never joins a real daily room.
